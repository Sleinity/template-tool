# Studio UI/UX and Design Fidelity Audit

## Executive assessment

Studio has a strong functional base: the five-step importer, native SDK validation, compact field cards, guarded edits, recovery, and export readiness are already in place. Recent Fields work resolved several findings from the [previous UI audit](/Users/niels/Documents/Projects/template-tool/docs/studio/UI_UX_AUDIT_20261011.md); the old delete-menu, keyboard-menu, Family field-preview, and bulky-card findings should not be reopened as current defects.

The main weakness is **continuity between task and interface**. Saved-template Settings opens at Designs instead of Fields; Checks can tell an expert that something is wrong without making the next action clear; Review repeats its decision; and the output editor gives users little help connecting a field to its location in the design. The visual system has useful tokens and shared components, but page-specific presentation and repeated status treatments make the product feel less coherent than its underlying SDK.

Studio is a credible *source example* for SDK integration, but is not yet a polished host reference. It is currently a [private application](/Users/niels/Documents/Projects/template-tool/apps/studio/package.json), not a supported UI package. The recommendation is to improve its workflows and document adaptable integration patterns without turning Studio components into a public SDK API.

**Audiences and journeys**

| Audience | Current journey | Main friction |
| --- | --- | --- |
| Template expert | Library → Designs → Fonts → Checks → Fields → Review → save | Repeated guidance and status; saved Settings starts at the beginning |
| Output creator | Library → Create output → edit fields and variants → autosave → export | Field and preview feel separate; some controls and thumbnails do not reflect available SDK data well |
| Host developer | Read Studio and SDK examples → adapt UI and services | Supported SDK boundary is sound, but branding and host-owned workflow choices need a clearer example map |

No P0 issue was established by this audit. Priorities below reflect user impact and likely frequency, not a new renderer or SDK assessment.

## Target experience and visual direction

Keep **two deliberately different modes**. The importer is a terse expert workflow: one task per step, actionable Checks, compact Fields, and one clear save decision. Output creation is a calm editing workspace: field controls on the left, a prominent linked design preview, immediate local input feedback, and a single export action governed by current SDK readiness.

Retain the panel-and-preview layout. Field focus should locate the corresponding design region; Fit design and Fit field should work like view controls, not change template geometry. Figma documents fit/selection zoom as navigation aids, while Framer and Canva similarly distinguish canvas viewing from content editing. That principle transfers to Studio without copying a full design tool’s complexity. [Figma zoom guidance](https://help.figma.com/hc/en-us/articles/360041065034-Adjust-your-zoom-and-view-options), [Framer canvas guidance](https://www.framer.com/help/articles/how-to-use-the-canvas/), [Canva page-view guidance](https://www.canva.com/help/page-view-settings/).

Use the existing typography and spacing tokens as the baseline. Standardize page title, section title, control label, supporting text, and technical metadata roles; align card padding and toolbar heights; reserve strong borders and color for selection, errors, and primary actions. Use one primary action per context, one current-state summary, inline correction near the control, and restrained transitions that respect reduced-motion settings. These are usability changes, not decorative restyling.

## Four-phase improvement roadmap

| Phase | Scope and expected result | Dependency and risk | Acceptance |
| --- | --- | --- | --- |
| **1. UX foundations** | Resolve S01–S04, S06, S08, S10, S12. Saved Settings opens at the right task; asset thumbnails and issue actions tell the truth; field focus connects to preview. | Reuse existing asset, binding, validation, selection, and inspection authorities. Risk is stale highlight or resource ownership if UI bypasses them. | Single/Family journeys, failed/retry states, save/reopen, latest-value PNG, keyboard focus and no new resource owner. |
| **2. Interface and component refinement** | Resolve S05, S07, S09, S11 and the reproduced parts of S15. Shorter copy, consistent value controls, less filter wrapping, one Review decision. | Local draft behavior for incomplete Date/Color input must remain intact. Avoid broad CSS overrides. | All seven field types, five choice types, Apply/Discard/Reset, 600/768/1200/1440 px, visual comparison of all pages. |
| **3. Interaction polish** | Resolve S13 and measure S16; refine field-to-preview navigation, loading feedback, focus return and transitions. | Performance work starts with a repeatable production workload; renderer semantics and readiness stay unchanged. | Paired latency/long-task trials, rapid edits and variant switching, StrictMode, reduced motion, no readiness or fidelity regression. |
| **4. SDK reference readiness** | Resolve S14. Document Studio’s host-owned layers, supported SDK calls, adaptable tokens and replaceable UI decisions; update copyable example journeys. | Studio remains private; do not expose its components as a supported SDK package without a separate API decision. | Packed public-entry-only examples for import, field editing, validation, Family selection, recovery and export; documented customization points and no private imports. |

Quick wins for the first pass: open Settings at Fields; retire stale success notices; consolidate Review readiness; simplify empty diagnostics; tighten step copy; make Fields filters collapse when wrapped; use the SDK asset resolver for output thumbnails; and add output Fit design/zoom controls. Each should have a focused before/after interaction check.

Before implementation, record current screenshots and source identity. Verify changes with Studio setup/recovery and field-rule workflows, keyboard and narrow-width checks, plus the existing SDK/API/boundary tests. If an edit changes renderer inputs or pixels, run the source-authoritative three-export gate and review any changed output rather than adjusting references or tolerances. Keep automated coverage, live observation, and source-only conclusions separate.

**Assumptions:** Studio remains a private, adaptable source example; output editing remains a panel with linked preview; full editing targets desktop/tablet widths from 768 px, while mobile retains Library, recovery and a clear way back. No SDK schema, persistence, renderer, or package-version change is proposed.
